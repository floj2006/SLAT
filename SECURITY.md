# Безопасность SLOT.

Короткий отчёт по проверке защиты. Я прогнал по локальной копии сервиса набор типовых атак (имитация, не на боевой сайт) и просмотрел код. Тест-скрипт лежит вне репозитория — он нужен был только для проверки.

## Что проверял и результат

Все 16 проверок пройдены.

| Атака / проверка | Результат |
| --- | --- |
| Создание/удаление данных без входа | Отклонено, **401** |
| Изменения под ролью «просмотр» (student) | Отклонено, **403** (защита на сервере, не просто скрытые кнопки) |
| Поддельный токен в заголовке | Отклонено, **401** |
| SQL-инъекция в логине (`admin' OR '1'='1`) | Не проходит, **401** |
| SQL-инъекция в поиске (`'; DROP TABLE ...`) | Безопасна: таблицы на месте, данные не утекли |
| Утечка пароля/хеша в ответах | Нет: сервер отдаёт только токен, логин и роль |
| XSS: `<script>` как название предмета | Хранится как обычный текст; React экранирует его при выводе |
| Профиль и действия после выхода (logout) | Токен сразу недействителен, **401** |
| Мусор вместо числа, номер пары = 99, отрицательный id | Отклонено проверкой схемы (**422**) или **404**, сервер не падает |
| Строка в 100 000 символов | Отклонена (**422**) после доработки — см. ниже |
| Перебор логинов по времени ответа | Закрыт после доработки — см. ниже |

## Почему базовая защита надёжна

- **Нет сырого SQL.** Все запросы к базе идут через ORM (SQLAlchemy) с параметрами, поэтому классические SQL-инъекции невозможны.
- **Проверка прав на сервере.** Каждый POST/PUT/DELETE требует токен администратора (`require_admin`). Обойти, отправив запрос напрямую (мимо интерфейса), нельзя.
- **Пароли не хранятся в открытом виде.** В базе только соль и хеш PBKDF2 (100 000 итераций). Сравнение хешей — функцией постоянного времени (`hmac.compare_digest`).
- **XSS не срабатывает.** React по умолчанию выводит любые строки как текст, а не как HTML.

## Что исправил по итогам проверки

1. **Ограничение длины текстовых полей.** Раньше можно было сохранить сколько угодно символов (принималась строка в 100 КБ) — это путь к замусориванию базы. Добавил `max_length` во все входные схемы (`schemas.py`): названия, ФИО, комментарии и т.д.
2. **Одинаковое время ответа при входе.** Раньше на несуществующий логин сервер отвечал почти мгновенно (~1 мс), а на существующий — после проверки хеша (~40 мс). По этой разнице можно было узнать, какие логины заведены. Теперь при неизвестном логине сервер всё равно считает хеш-заглушку, и время ответа одинаковое (проверено: разница 4%).

Обе доработки закреплены автотестами (`test_max_length_rejected`, `test_unknown_user_same_message`).

## Что осталось сделать перед настоящим использованием в колледже

Это не дыры в текущем учебном проекте, а то, что нужно для публичной эксплуатации. По убыванию важности:

1. **Ограничение попыток входа (rate limiting).** Сейчас пароль можно подбирать без ограничений. Нужна блокировка после нескольких неудачных попыток. На Vercel для этого нужно внешнее хранилище (например, Upstash Redis) — встроенная память там не годится, потому что каждый запрос запускается заново.
2. **Срок жизни токенов.** Сейчас токен действует, пока пользователь снова не войдёт или не выйдет. Стоит добавить срок (например, сутки) и обновление.
3. **Токены хранятся в базе открытым текстом.** Если база утечёт, активные токены можно использовать. Лучше хранить их хеш, как пароли.
4. **Сильные пароли и их смена.** Демо-пароли (`admin123`, `student123`) — только для показа. В работе — сложные пароли и смена через интерфейс.
5. **Постоянная база и резервные копии.** Сейчас на Vercel база временная (`/tmp`). Для реальной работы — Postgres с бэкапами.
