## Часть 1. Презентация продукта (3–5 минут)

**Проблема.** В колледже расписание публикуют большими Excel-таблицами. С телефона их неудобно читать: нужно масштабировать, искать свою группу среди десятков колонок, а замены часто публикуют отдельным файлом или сообщением. Изменить таблицу может только тот, у кого есть файл, и никто не проверяет, что преподаватель не стоит в двух аудиториях одновременно.

**Решение.** SLOT. — веб-платформа расписания. Студент выбирает группу и за пару секунд видит пары на сегодня: какая идёт сейчас, где была замена, какая пара отменена. Преподаватель находит своё расписание через поиск. Учебная часть редактирует расписание в админ-панели, а сервер не даёт создать конфликт.

**Почему Figma.** Сначала я спроектировал интерфейс, а потом писал код. В Figma собрана дизайн-система: цвета, типографика, отступы, компоненты с состояниями. Благодаря этому интерфейс единообразный, и в коде я переносил уже готовые решения, а не придумывал на ходу. Токены Figma и CSS-переменные в коде совпадают один к одному.

**Как проектировал интерфейс.** Главный принцип — «найти расписание за несколько секунд». Поэтому главная — это сразу поиск и карточки групп. Статусы занятий выделены цветом и иконкой: зелёный — идёт сейчас, жёлтый — замена, фиолетовый — другая аудитория, красный — отмена. Один яркий акцент (синий) используется только для активного и важного. Мобильная версия — с нижней панелью вкладок, как в приложениях.

**Технологии.** Frontend — React + Vite, CSS Modules, React Router, Lucide-иконки. Backend — Python, FastAPI, SQLAlchemy, база SQLite. Связь — REST API и запросы fetch.

**Как работает система.** Браузер отправляет HTTP-запрос, FastAPI проверяет данные и права, через ORM читает или меняет таблицы в SQLite и возвращает JSON. React показывает этот JSON. Шесть таблиц: группы, преподаватели, предметы, аудитории, занятия и изменения расписания, плюс пользователи для входа. Изменять данные может только администратор: это проверяет сервер по токену, а не просто скрытие кнопок.

## Часть 4. Вероятные вопросы по коду

**1. Как frontend получает данные с сервера?**
Через `fetch` в функции `request()` в `src/api/api.js`. Компоненты вызывают готовые функции, например `getGroupSchedule(id, week)`, внутри `useEffect`, и кладут ответ в `useState`.

**2. Что такое компонент и props?**
Компонент — функция, которая возвращает разметку. Props — её входные данные. Например, `LessonCard` получает `item` (занятие) и `status`, а рисует карточку.

**3. Зачем useState?**
Чтобы React помнил значение и перерисовывал страницу, когда оно меняется. Например, `view` в `ScheduleScreen` переключает «День / Неделя».

**4. Когда срабатывает useEffect?**
После отрисовки и каждый раз, когда меняется что-то из списка зависимостей. В `ScheduleScreen` — когда меняется `weekStart`, поэтому стрелки недели загружают новую неделю.

**5. Что делает async/await?**
Позволяет дождаться ответа сервера, не замораживая страницу. `await login(...)` ждёт ответа, ошибки ловятся в `try/catch`.

**6. Какие HTTP-методы используются и зачем?**
GET — получить, POST — создать, PUT — изменить, DELETE — удалить. Например, `PUT /api/lessons/5` изменяет занятие с id 5.

**7. Какие таблицы есть в базе и как они связаны?**
groups, teachers, subjects, classrooms, lessons, schedule_changes, users. Занятие (`lessons`) ссылается внешними ключами на группу, предмет, преподавателя и аудиторию. Изменение ссылается на занятие и, при необходимости, на нового преподавателя или аудиторию.

**8. Что такое ORM и зачем SQLAlchemy?**
ORM связывает Python-классы с таблицами. Вместо SQL пишем `db.query(Lesson).filter(...)`, а SQLAlchemy сам генерирует SQL. Код короче и защищён от SQL-инъекций.

**9. Что такое CRUD в вашем проекте?**
Создание, чтение, изменение и удаление. Есть для всех справочников, занятий и замен: эндпоинты POST/GET/PUT/DELETE и кнопки в админ-панели.

**10. Как работает авторизация?**
POST `/api/auth/login` проверяет пароль по хешу и выдаёт случайный токен. Frontend хранит его в localStorage и отправляет в заголовке `Authorization: Bearer ...`. Функция `require_admin` проверяет токен (иначе 401) и роль (иначе 403).

**11. Почему нельзя просто скрыть кнопки?**
Запрос можно отправить в обход интерфейса — например, из `/docs` или Postman. Поэтому проверка стоит на сервере. Это видно, если войти как `student`.

**12. Как хранятся пароли?**
Не открытым текстом, а как соль + хеш PBKDF2 (`auth.py`). При входе пароль хешируется с той же солью и сравнивается.

**13. Как сервер не даёт поставить две пары в одно время?**
`check_conflicts` в `routers/lessons.py` ищет занятия в тот же день и ту же пару с пересекающимся типом недели и проверяет группу, преподавателя и аудиторию. Если что-то занято — ответ 409 с объяснением.

**14. Как учитываются чётные и нечётные недели?**
У занятия есть `week_type`: both / odd / even. `week_type_of()` определяет чётность по номеру ISO-недели, `build_week()` оставляет только подходящие занятия.

**15. Как замены попадают в расписание?**
Замены хранятся отдельно, с датой. `build_week()` берёт изменения за неделю и прикладывает их к занятиям по паре (id занятия, дата). Карточка видит `change` и показывает статус.

**16. Что такое Pydantic-схемы?**
Описание формата JSON. Они проверяют входные данные: например, `pair_number` от 1 до 6. Неверные данные отклоняются с кодом 422 ещё до кода эндпоинта.

**17. Зачем CSS Modules?**
Классы из `LessonCard.module.css` действуют только внутри `LessonCard`, поэтому одинаковые имена (`.time`, `.body`) в разных компонентах не конфликтуют.

**18. Как сделана тёмная тема?**
Все цвета — CSS-переменные в `tokens.css`. Кнопка ставит `<html data-theme="dark">`, и блок `[data-theme='dark']` переопределяет переменные. Компоненты менять не нужно.

**19. Как сделана адаптивность?**
Через `@media (max-width: 767px)`: боковое меню скрывается, появляется нижняя панель, сетка групп становится в одну колонку. Брейкпоинт взят из макета.

**20. Как проверить, что всё работает?**
В backend 10 автотестов (`python -m pytest -q`): CRUD, конфликты, 401/403, валидация. API можно проверить вручную в `/docs`. Frontend — пройти сценарий из части 3.

**Запасной вопрос: проверяли ли вы безопасность?**
Да, прогнал по сервису типовые атаки: вход без прав, подделку токена, SQL-инъекции в логине и поиске, XSS, мусор во входных данных — всё отбивается (отчёт в `SECURITY.md`). По итогам добавил ограничение длины полей и выровнял время ответа при входе, чтобы нельзя было перебором узнать существующие логины.

**Запасной вопрос: как вы продумывали тексты интерфейса?**
Есть словарь терминов и правила в `COPY.md`. Одно понятие называется одним словом везде. Ошибки говорят, что случилось и что делать: «Аудитория 214 в это время занята группой ИС-22. Выберите другую аудиторию». Числа склоняются: «1 пара, 3 пары, 5 пар».

**Запасной вопрос: что бы вы улучшили?**
Импорт расписания из Excel, уведомления о заменах, отдельный вход для преподавателей и хранение токенов со сроком действия.
